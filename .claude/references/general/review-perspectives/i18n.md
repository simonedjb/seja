# I18N — Internationalization

## Essential

- [P0] Are all user-facing strings using i18n keys (not hardcoded)?
- [P0] Are both locale files (pt-BR.json, en-US.json) and .po catalogs updated in sync?
- [P0] Are resource bundles structured so new locales add without code changes, with automated extraction/merge pipelines preventing stale or orphaned keys?
- [P0] Are text pipelines fully Unicode-safe (UTF-8, NFC normalization, no mid-codepoint truncation), with grapheme clusters handled for truncation/counting/cursor movement?

## Standard

- [P2] Do locale-specific characters (diacritics, ligatures, non-BMP codepoints) round-trip correctly through storage, retrieval, and display without substitution, mojibake, or loss?
- [P1] Are locale fallback chains tested (missing key in primary locale falls back gracefully)?
- [P1] Are date, number, and currency formats locale-aware in both backend and frontend, using locale-sensitive formatters (ICU MessageFormat, Intl APIs) for plurals, ordinals, relative time, units, and number grouping?
- [P1] Does the translation workflow integrate with a TMS (Crowdin, Phrase, Lokalise) via CI (no manual file copying)?
- [P1] Does the UI adapt to RTL (Arabic, Hebrew) with correct layout/icon mirroring and bidi isolation (`dir="auto"` or Unicode bidi controls)?
- [P2] Are culturally sensitive elements (colors, imagery, idioms, name/address order) reviewed for each target market?
- [P2] Do search indexes and sort collations use locale-aware rules (ICU collation, accent-insensitive matching)?
- [P1] Are internationalized interfaces accessible (correct `lang` per fragment, screen-reader-friendly locale switches, contrast/spacing for Devanagari or CJK)?
- [P2] Are user-visible identifiers (usernames, domain names, URLs) checked for homoglyph/homograph ambiguity, with Unicode confusable detection or Punycode display applied to prevent visual spoofing attacks? (CWE-1007)
- [P2] Is output encoding context-specific — HTML entity encoding for HTML contexts, URL percent-encoding for query strings, JSON string escaping for JSON, and shell quoting for commands — never mixed or applied in the wrong context? (CWE-838)
- [P1] Are datetimes stored in UTC and converted using IANA timezone identifiers? Is the user's local timezone captured (from browser, OS, or explicit preference) and passed to locale-sensitive formatters (ICU `DateFormat`, `Intl.DateTimeFormat`) for all temporal display?
- [P1] Does the application detect the user's preferred locale from `Accept-Language`, OS locale, or explicit user preference? Is it negotiated against the list of supported locales using BCP 47 subtag stripping (RFC 4647 lookup) rather than exact-match or ad-hoc logic? Is the resolved locale persisted across sessions?
- [P1] Is the HTML `lang` attribute set to a valid BCP 47 tag on the `<html>` element for every locale? Are embedded fragments in a different language (e.g., a French quotation on an English page) individually marked with `lang` to ensure correct hyphenation, quotation marks, and screen reader pronunciation?
- [P1] Is pseudo-localization (e.g., expanding strings by 30–60%, wrapping in brackets, replacing ASCII with accented equivalents) run in CI on every build to detect layout overflow, clipped text, and hardcoded strings before real locale catalogs are produced?
- [P2] Do text input fields accept Unicode characters for all supported locales (no ASCII-only validation for names, addresses, or identifiers)? Do they correctly handle IME composition events (not triggering `input` handlers mid-composition)? Is field validation parameterized by locale for formats like postal codes, phone numbers, and ID documents?

## Deep

- [P3] Is there a documented locale-tier strategy (full human translation, MT+review, MT-only) with per-locale completeness and freshness metadata surfaced in the TMS and visible to stakeholders?
- [P3] Are RTL layouts built with logical CSS properties (`margin-inline-start`, `padding-block-end`, etc.) instead of directional overrides, eliminating the need for `[dir="rtl"]` style blocks? Is `<bdi>` used to isolate embedded user-generated content with unknown directionality (usernames, external strings) to prevent bidi spillover?
- [P3] Is text ingested from external systems (file uploads, third-party APIs, legacy databases) explicitly normalized to NFC before storage and comparison? Are equality checks on user-visible strings (usernames, search terms) performed on NFC-normalized forms to prevent silent mismatches between visually identical strings in different normalization forms?
- [P4] Does every extractable localization key carry context metadata in the TMS (screenshot, surrounding component name, character limit, example placeholder values)? Is translation memory (TM) enabled across product surfaces so repeated strings (error messages, button labels) are translated consistently and at reduced cost?
