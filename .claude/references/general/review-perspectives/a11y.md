# A11Y — Accessibility

## Essential

- [P0] Does this meet WCAG 2.2 Level AA conformance requirements, and where applicable, target WCAG 2.2 Level AAA criteria for contrast, keyboard navigation, and screen readers?
- [P0] Are interactive elements focusable with visible focus indicators?
- [P0] Are focus management and live region announcements tested with actual screen readers (NVDA, VoiceOver)?
- [P0] Are all interactive custom components (modals, dropdowns, pickers) fully keyboard-operable with documented shortcuts?
- [P0] Do dynamic content updates (SPAs, AJAX regions, toasts) produce correct screen-reader announcements via aria-live, verified across NVDA, JAWS, and VoiceOver?
- [P0] Can every workflow be completed keyboard-only, with no focus traps, logical tab order, and skip-navigation links?
- [P0] Does the product satisfy applicable legal mandates (ADA, Section 508, EN 301 549, EAA), with a published accessibility statement?
- [P0] Do all images, icons, charts, infographics, and other non-text content have correct accessible names (via `alt`, `aria-label`, or `aria-labelledby`), and are purely decorative elements marked with `aria-hidden="true"` or `alt=""`?
- [P0] Do pages use the eight ARIA landmark roles (or their HTML equivalents: `main`, `nav`, `header`, `footer`, `form`, `aside`, `section`) to identify major content areas, and is all visible content contained within an appropriate landmark region?

## Standard

- [P1] Are ARIA labels and roles used where semantic HTML is insufficient?
- [P1] Do color-dependent cues provide a non-color alternative, and do palettes pass WCAG AA/AAA contrast ratios?
- [P1] Are instructions and error messages in plain language; do sessions warn before timeout and allow extension (WCAG 2.2.1); do animations honor prefers-reduced-motion or provide a pause control?
- [P1] Has a formal WCAG 2.2 Level AA audit been performed, with AAA criteria evaluated where applicable, and all failures tracked to resolution?
- [P1] Are ARIA roles/states/properties used only when native HTML is insufficient, and do composite widgets follow WAI-ARIA Authoring Practices?
- [P1] Can drag/gesture/hover interactions be performed via alternative single-pointer or switch-accessible controls (target >= 44x44 CSS px)?
- [P1] Does the UI honor the `prefers-reduced-motion` CSS media query by pausing or eliminating non-essential animations, transitions, and parallax effects? Does auto-rotating content (carousels, marquees, live feeds) stop on keyboard focus and provide a pause/stop control per WCAG 2.2.2?
- [P1] When modal dialogs or overlay panels open, is background content made truly inert for all users (not just announced as modal via `aria-modal="true"`)? Does focus move to a logical element within the dialog on open, is the tab sequence contained within the dialog, and does focus return to the triggering element on close?
- [P1] Do authentication and verification flows (login, MFA, CAPTCHA, account recovery) avoid requiring users to complete cognitive function tests without providing an alternative method that does not rely on memorization, transcription, or pattern recognition per WCAG 3.3.8?
- [P1] Do all drag-and-drop and multi-point or path-based gesture interactions have a single-pointer alternative per WCAG 2.5.1? Do interactive touch targets meet the WCAG 2.5.8 minimum of 24×24 CSS px (AA), and where feasible, the 44×44 CSS px AAA target per WCAG 2.5.5?
- [P1] Are all form inputs, interactive controls, and custom widgets associated with visible labels via `<label for="">`, `aria-labelledby`, or `aria-label`? Are accessible names verified to produce correct AT announcements in at least NVDA+Chrome and VoiceOver+Safari, not just inspected in the accessibility tree?
- [P2] Are generated PDFs tagged with correct structural markup and verified with accessibility checkers (PAC, Acrobat)?

## Deep

- [P3] Has an expert cognitive walkthrough assessed primary workflows for reading level (WCAG 3.1.5), step count, error recovery burden, and working memory demand? Are consistent help mechanisms present at predictable locations (WCAG 3.2.6), and does the product avoid requiring users to re-enter information already provided in the same session (WCAG 3.3.7)?
